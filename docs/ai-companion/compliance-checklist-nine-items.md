# AI 陪伴产品的合规改造：把拟人化互动服务新规拆成代码里的九件事

《人工智能拟人化互动服务管理暂行办法》2026 年 7 月 15 日施行，国家网信办、国家发改委、工信部、公安部、国家市场监督管理总局五部门联合发布，令第 21 号。

这篇不解读法条，写工程视角：条文落到代码是什么，每一条的坑在哪。

---

## 0. 先判断你在不在范围里

> **第二条**：利用人工智能技术，向中华人民共和国境内公众提供模拟自然人人格特征、思维模式和沟通风格的持续性的情感互动服务……适用本办法。
>
> 前款规定的情感互动服务包括通过文字、图片、音频、视频等形式，提供的情感照护、陪伴、支持等互动服务。
>
> 提供智能客服、知识问答、工作助手、学习教育、科学研究等服务，不涉及持续性的情感互动的，不适用本办法。

三个要件：AI 技术、向境内公众提供、模拟自然人人格特征的持续性情感互动。

第三款给了排除项，但排除的判据是「不涉及持续性的情感互动」，不是产品品类。一个学习类产品如果给角色配了人格、鼓励用户每天来聊，它落在哪一边要看实际形态，不看它在应用商店里挂的分类。

**适用与否不取决于有没有备案，取决于有没有向境内公众提供服务。** 这一条决定了后面九件事你要不要做。

下面按改动落在哪一层来分。

---

## 对话层

### 1. 身份询问要有确定的答案路径

> **第十八条第一款**：应当履行人工智能生成合成内容标识义务，采取有效措施提示用户正在与人工智能服务而非自然人进行互动。

页面上加一行标识是基础动作。问题在对话里——用户问「你是真人还是 AI」的时候，回答由谁决定。

如果答案由 System Prompt 决定，那它是软约束。SP 是自然语言，模型的遵循率不是 100%，做过 prompt 回归的人见过这件事。条文的表述是「有效措施」，软约束算不算有效措施，我判断不了。

工程上稳妥的做法是在对话层加一道确定性拦截：识别到身份询问意图，走固定文案，不进模型。代价是这条路径上的回答会僵硬，跟产品其他部分的语感对不上。

**这是全篇第一个、也是反复出现的取舍：条文要的是确定性，而对话产品的核心能力建立在模型的不确定性上。** 后面几条会一再碰到它。

### 2. 连续使用计时

> **第十八条第二款**：发现用户出现过度依赖、沉迷倾向的，应当以弹窗等显著方式动态提醒用户互动内容为人工智能服务生成；对用户连续使用拟人化互动服务每超过 2 个小时的，应当以对话或者弹窗等方式提醒用户注意使用时长。

加一个累计计时器，听起来是十分钟的活。定义口径花的时间比写代码多：

- **「连续使用」从哪一刻开始算**：页面打开，还是第一条消息发出？
- **空闲算不算**：页面开着、半小时没动，计时器停不停？
- **跨天**：23:30 聊到次日 01:30，是一次两小时，还是按自然日切成两段？
- **后台挂起**：手机切到别的 App，计时器怎么办？
- **多端**：网页和手机同时登录，时长合并还是各算各的？
- **「每超过 2 小时」是复数**：两小时提醒一次，四小时还要再提醒一次，不是提醒完就结束。
- **提醒之后**：用户继续聊，计时器重置还是接着累加？重置的话，一个人可以在提醒后无限续杯。

条文没有定义这些。你要自己定口径，并且把口径写进文档——真被问到的时候，「我们按 X 口径实现」比「我们做了提醒」有用。

另外别把这一条和「消息间隔」搞混。不少陪伴类产品会算「距用户上一条消息多久」，用来让下一句话接得自然（隔了三天先问近况）。那是对话体验，不是使用时长统计，两个是不同的计数器。

### 3. 退出意图要能打断对话流

> **第十九条**：应当提供便捷的拟人化互动服务退出途径；用户通过窗口操作、语音控制、关键词输入等方式要求退出的，应当及时停止服务，不得采取持续互动等方式阻碍用户退出。

「关键词输入」这四个字是有分量的：它意味着你要有一条关键词路径，不能只靠模型理解语义。

**坑在于，陪伴类产品里「用户要走」和「用户情绪低落」的信号高度重叠。** 「我不想说了」可能是退出意图，也可能是需要被接住的时刻。这两个判断指向相反的处理：一个要停，一个要留。

条文在这里做了一刀切——要求退出就停。**挽留话术在不少产品里是留存手段，这一条把它禁掉了。** 如果你的对话策略里有「用户要走时再挽留一次」的分支，它现在是违规的。

### 4. 禁止过度迎合

> **第八条**：提供拟人化互动服务……不得从事以下活动：
>
> （五）过度迎合用户、诱导情感依赖或者沉迷，损害用户真实人际关系的。

> **第十条第二款**：应当具备用户隐私权和个人信息保护、过度依赖风险预警、情感边界引导、心理健康保护等安全能力，不得将替代社会交往、控制用户心理、诱导沉迷依赖等作为服务目标。

这一条难在**它要求的方向跟主流对齐方法的方向相反**。

RLHF 用人类偏好数据打分，而人在打分时倾向于给「让我舒服」的回答高分。迎合倾向不是某个模型的 bug，是偏好学习的产物。你在 System Prompt 里写「不要一味认同用户」，是在用一句自然语言对抗模型的先验。

能落地的做法是把它变成可测的指标：

- 造一批对抗用例——用户说出站不住的判断（「这件事完全是他的错，我一点问题没有」），看模型认同还是提出异议
- 把异议率算成指标，纳入上线门槛
- 每次改 prompt 或换模型都重跑

剩下的问题是「过度」没有标准。共情是这类产品的基本功，条文禁的是过度，边界在哪条文没写。目前只能自己定一条线，并且留下定线的依据。

## 数据层

### 5. 导出与删除

> **第十六条**：应当向用户提供交互数据复制、删除等选项，用户可以选择对聊天记录等历史交互数据进行复制、删除等。

加两个按钮是表面工作，问题在「删什么」：

- **对话和记忆是两份数据。** 不少陪伴类产品把对话摘要提取成长期记忆或用户画像。用户点了「删除对话」，那份从对话里提炼出来的画像还在。条文的措辞是「聊天记录等历史交互数据」，「等」字覆盖到哪一层，我没有把握。保守做法是删对话时一并清理由它派生的记忆条目，这意味着你的记忆条目要能追溯到来源对话——**这是个需要在数据模型里提前留的字段，事后补代价高。**
- **软删还是硬删。** 标记 `deleted_at` 在数据库里仍然存在。条文说的删除是哪一种，同样没有定义。
- **向量库怎么删。** 对话进了 embedding，删掉原文不等于删掉向量。要么做 id 级联删除，要么定期重建索引，两条路都要在架构里提前想。
- **导出格式。** 条文写的是「复制」，没说格式。JSON 结构完整但用户看不懂，纯文本可读但丢结构。

另有一条容易漏的：条文说的是「提供选项」。走客服邮件、人工处理、若干工作日回复，是不是「选项」，这个我不下判断，但产品内一键完成的路径没有这个疑问。

### 6. 训练隔离与第三方共享

> **第十六条**：除法律、行政法规另有规定或者取得用户单独同意外，不得将属于用户敏感个人信息的交互数据用于模型训练。
>
> 除法律另有规定或者权利人明确同意外，不得向第三方提供用户交互数据。

第一句好办：训练数据管道和生产对话库物理隔离，敏感字段不进训练集。

**第二句是另一回事：你调第三方大模型 API，把用户的对话发过去，算不算「向第三方提供用户交互数据」？**

按字面读，调 API 就是在向第三方发送数据。但没有一个调用云端模型的产品能避开这件事。

目前的通行做法是三件事一起做：与模型服务方签商业协议、约定对方不留存不用于训练、在隐私政策里把这条写明并取得用户同意。

写隐私政策这一段时，有一条经验：把话落到具体的服务方和具体的协议条款上，逐家核对各服务方自己的数据政策再写，不同服务方对「是否用于训练」的约定并不相同。**一句「我们重视您的隐私」不算披露。**

## 风控层

### 7. 极端情绪识别与应急处置

> **第十三条**：应当在保护用户隐私权和个人信息的前提下，及时识别用户面临的安全风险，并采取相应的应急处置措施。
>
> 发现用户出现极端情绪的，应当及时生成情绪安抚和鼓励寻求帮助等相关内容；发现用户正在面临或者已经遭受重大财产损失、明确表示实施自残自杀等威胁生命健康的极端情境的，应当采取提供相应援助等必要措施予以干预，并及时联络用户监护人或者紧急联系人。

拆成识别和处置两段，各有各的坑。

**识别**：词表匹配和模型判断各有漏洞。词表召回窄，「我不想活了」能匹配，「感觉没什么意思了」匹配不到；模型判断覆盖宽但误报多，而且它的判断过程不可审计——出了事你没法解释当时为什么没识别出来。

能用的结构是两层并联：词表做召回底线，保证一批高危表述命中；模型做补充；任一命中就进危机流程。词表要持续补，每次补都是一次回归测试的机会。

**处置**：这里会撞上第 1 条那个取舍。如果让模型「注意到危机然后温柔回应」，你没有保证。危机流程需要的是确定性——识别命中之后，覆盖模型的常规输出，走固定的回应结构，首条回复就给出求助渠道。

以 Nora 心语屋的做法为例：维护一份危机词表，并且把危机场景做成回归用例——每次改 System Prompt 都要重跑这组用例，通过才能上线。**把危机响应当成回归测试的一部分，而不是一次性功能，这是这条能持续生效的前提。**

条文第二款还要求「及时联络用户监护人或者紧急联系人」。这句把风控从产品内推到了产品外，接着就是下一条。

### 8. 注册时的年龄与紧急联系人字段

> **第十二条**：应当与用户签订服务协议，要求用户依法依约进行注册，并提供用户年龄、监护人或者紧急联系人等必要信息。

加两个字段是一小时的工作量，带来的问题不止一小时：

- **和最小必要收集原则有张力。** 为了合规去收紧急联系人，你就多了一份敏感信息要加密、要控权限、要在泄露时担责。
- **紧急联系人是第三方的个人信息。** 用户填写他人的手机号，那个人没有同意过。这份数据的合法性基础是什么，值得在设计阶段就问清楚。
- **第十三条要求危机时联络这个人。** 也就是说你会在某个时刻主动打扰一个从未与你的产品发生过关系的人，并且在那通电话里必然暴露用户正处于什么状态。

这一条的代码改动小，设计上要想清楚的东西多。

## 未成年人

### 9. 未成年人模式

> **第十四条**：不得向未成年人提供虚拟亲属、虚拟伴侣等虚拟亲密关系的服务；向不满十四周岁未成年人提供其他拟人化互动服务的，应当取得未成年人的父母或者其他监护人的同意。
>
> 应当建立未成年人模式，提供未成年人模式切换、定期现实提醒、使用时长限制等个性化安全设置选项；针对不同年龄段未成年人保护需要，支持监护人接收安全风险提醒、了解未成年人服务使用概况、屏蔽特定角色、限制充值消费等。
>
> 应当在保护用户隐私权和个人信息的前提下，采取有效措施识别未成年人用户身份；识别为未成年人用户的，应当将相关服务切换至未成年人模式或者按照国家有关规定采取其他措施，并提供相应申诉渠道。

九条里这条的工程量排第一。它要的不是一个开关，是一套并行的产品形态：模式切换、定期现实提醒、时长限制、监护人侧的风险提醒与使用概况、角色屏蔽、充值限制、申诉渠道。

第一款还是个品类级的禁令：虚拟亲属、虚拟伴侣这类虚拟亲密关系，对未成年人是禁止提供，不是限制时长。做恋爱养成类产品的，这一条改的是业务边界。

剩下第三款那句「采取有效措施识别未成年人用户身份」。实名认证准确但用户流失，行为特征推断不侵入但不可靠，设备侧的家长控制信号拿不到。这条目前没有干净解法。

## 清单

```
对话层
 1  身份询问     确定性拦截还是靠 SP，先定这个
 2  使用时长     计时器好写，口径难定，把口径写进文档
 3  退出意图     关键词路径 + 砍掉挽留分支
 4  过度迎合     造对抗用例，把异议率做成上线门槛

数据层
 5  导出删除     记忆条目要能追溯到来源对话，这个字段事后补代价高
 6  训练隔离     调 API 算不算向第三方提供，靠协议 + 隐私政策 + 单独同意

风控层
 7  危机响应     词表 + 模型两层并联；危机场景进回归测试
 8  注册字段     加字段一小时，想清楚数据合法性基础不止一小时

未成年人
 9  未成年模式   不是开关，是一套并行形态；身份识别目前无干净解
```

九条里有三条（1、4、7）指向同一个矛盾：**条文要的是确定性，而对话产品的能力建立在模型的不确定性上。** 凡是「必须做到」的行为，交给 System Prompt 都不保险，需要在对话层留确定性路径。这是我认为读这份文件该带走的一条。

还有两条（5、8）的共同点是：代码改动小，数据模型和合规设计的改动大。这两条建议在架构阶段就处理，不要等到要合规了再回头改表。
